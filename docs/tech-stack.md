# 기술 스택 선택 근거

## 결론

| 영역 | 선택 |
|---|---|
| 웹 | Next.js (App Router) + Tailwind CSS v4 + shadcn/ui, Vercel 배포 |
| 데이터 | DB 없음. 크롤링 결과는 레포의 JSON 파일, 체크 응답은 저장하지 않음 |
| 크롤러 | Node 스크립트, GitHub Actions에서 주기 실행 후 JSON을 커밋 → Vercel 재배포 |
| 분석 | Google Analytics 4 |

## 판단 기준

과제는 48시간 안에 **문제 정의와 UX**로 평가받는다. 제출물에는 배포 링크가 반드시 들어가고, 솔루션에 크롤링이 필수다. 그래서 기준을 다음 세 가지로 잡았다.

1. 문제 해결과 화면에 쓰는 시간을 최대화한다. 인프라와 보일러플레이트에 쓰는 시간은 최소화한다.
2. 처음부터 배포된 상태로 개발한다. 배포는 마지막 단계가 아니다.
3. 크롤링이 실패해도 서비스는 살아 있어야 한다.

## 선택 이유

- **Next.js + Vercel**: 화면과 서버 로직을 한 코드베이스에서 처리한다. push하면 바로 배포되고, 미리보기 URL도 자동으로 생긴다.
- **DB 없음**: 서버에 저장할 데이터가 크롤링한 병원 목록(수백 건, 주 단위로 바뀜)뿐이다. JSON 파일로 두면 페이지를 정적으로 생성할 수 있고, 데이터 이력은 git이 대신 관리한다.
  - **체크 응답**: 결과는 클라이언트에서 계산한다. 응답은 건강정보(민감정보)라서 저장하지 않는 편이 동의·보관·파기 부담이 없고, "기록이 남지 않는다"는 것 자체가 신뢰 요소가 된다.
  - **결과 공유 링크**: 응답을 링크의 해시(`/result#…`)에 인코딩한다. 해시는 브라우저 밖으로 전송되지 않아서 GA나 서버 로그에 응답이 남지 않는다. 문항이 바뀌어도 해석되도록 코드에 버전을 붙인다.
  - **지표**: 외부 링크 클릭과 퍼널은 GA4 이벤트로 수집한다. 개별 응답은 보내지 않고 결과 단계만 보낸다.
- **크롤러 + GitHub Actions**: 크롤링을 사용자 요청 시점에서 분리해, 미리 수집해 저장해두는 배치 방식으로 운영한다. 가격비교·메타검색 서비스가 쓰는 일반적인 구조다. 대상 사이트(레즈메드, 대한수면연구학회)가 정적 HTML이라 헤드리스 브라우저 없이 `fetch`로 수집한다. 수집에 실패하면 커밋하지 않으므로 이전 데이터로 서비스가 유지된다. Actions는 무료이고 실행 로그가 남으며 cron 실행과 수동 실행을 모두 지원한다.

## 검토한 대안

| 대안 | 제외 이유 |
|---|---|
| Django + DRF + Postgres (초기 구성) | API, 직렬화, 배포 인프라를 직접 만들어야 해서 48시간 중 상당 부분이 문제 해결이 아닌 곳에 쓰인다. |
| Supabase (Postgres + RLS) | 당사자 리포트의 "가볼게" 상태 추적이 확장 단계로 빠지면서 사용자 데이터를 저장할 일이 없어졌다. 병원 목록만을 위해 스키마·RLS·키 관리를 두는 것은 과하다. |
| 요청 시점 크롤링 (Route Handler) | 응답이 느려지고, 차단·장애가 곧바로 서비스 장애가 된다. |
| Vercel Cron + 함수에서 크롤링 | 실행 시간 제한이 있고, Hobby 플랜은 하루 1회만 실행된다. |
| 상주 워커 (Railway, Fly) | 이 규모에는 운영 부담이 과하다. |

## 감수한 트레이드오프

- 데이터가 바뀔 때마다 재배포된다. 병원 목록은 주 1회 갱신이면 충분해서 문제없다.
- 데이터는 크롤링 주기만큼 늦게 반영된다. 화면에 마지막 수집 시각을 보여주는 방식으로 보완한다.
- 공유 링크는 만료·취소할 수 없다. 저장하지 않는 구조의 당연한 결과다.
- 사용자 데이터 저장이 필요한 기능(거부 이유별 리포트, "가볼게" 알림)이 들어오면 그때 DB를 붙인다.
