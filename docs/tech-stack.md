# 기술 스택 선택 근거

## 결론

| 영역 | 선택 |
|---|---|
| 웹 | Next.js (App Router) + Tailwind CSS v4 + shadcn/ui, Vercel 배포 |
| DB · 인증 · 스토리지 | Supabase (Postgres + RLS) |
| 크롤러 | Node 스크립트, GitHub Actions에서 주기 실행 후 Supabase에 upsert |

## 판단 기준

과제는 48시간 안에 **문제 정의와 UX**로 평가받는다. 제출물에는 배포 링크가 반드시 들어가고, 솔루션에 크롤링이 필수다. 그래서 기준을 다음 세 가지로 잡았다.

1. 문제 해결과 화면에 쓰는 시간을 최대화한다. 인프라와 보일러플레이트에 쓰는 시간은 최소화한다.
2. 처음부터 배포된 상태로 개발한다. 배포는 마지막 단계가 아니다.
3. 크롤링이 실패해도 서비스는 살아 있어야 한다.

## 선택 이유

- **Next.js + Vercel**: 화면과 서버 로직(서버 컴포넌트, Server Action)을 한 코드베이스에서 처리한다. push하면 바로 배포되고, 미리보기 URL도 자동으로 생긴다.
- **Supabase**: DB, 인증, 행 단위 권한(RLS), 타입 생성을 직접 만들 필요가 없다. 클라이언트가 DB를 직접 조회하므로 조회용 API 서버가 필요 없다. 데이터는 표준 Postgres이고 마이그레이션은 SQL 파일로 관리한다. 그래서 나중에 이전해야 해도 종속이 적다.
- **크롤러 + GitHub Actions**: 크롤링을 사용자 요청 시점에서 분리해, 미리 수집해 저장해두는 배치 방식으로 운영한다. 가격비교·메타검색 서비스가 쓰는 일반적인 구조다. 대상 사이트가 차단하거나 느려도 사용자 화면에는 영향이 없다. Actions는 무료이고 Playwright가 돌아가며 실행 로그가 남는다. cron 실행과 수동 실행을 모두 지원한다.

## 검토한 대안

| 대안 | 제외 이유 |
|---|---|
| Django + DRF + Postgres (초기 구성) | API, 직렬화, 배포 인프라를 직접 만들어야 해서 48시간 중 상당 부분이 문제 해결이 아닌 곳에 쓰인다. |
| 요청 시점 크롤링 (Route Handler) | 응답이 느려지고, 차단·장애가 곧바로 서비스 장애가 된다. |
| Vercel Cron + 함수에서 크롤링 | 실행 시간 제한이 있고, Hobby 플랜은 하루 1회만 실행된다. 헤드리스 브라우저를 올리기도 어렵다. |
| Supabase Edge Function + pg_cron | Deno 런타임이라 헤드리스 브라우저를 쓸 수 없다. |
| 상주 워커 (Railway, Fly) | 이 규모에는 운영 부담이 과하다. |

## 감수한 트레이드오프

- 비즈니스 로직이 RLS 정책과 서버 컴포넌트에 나뉘어 들어간다. 그래서 권한 규칙은 마이그레이션 파일 한 곳에서만 관리한다.
- 데이터는 크롤링 주기만큼 늦게 반영된다. 화면에 마지막 수집 시각을 보여주는 방식으로 보완한다.
