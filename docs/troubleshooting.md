## 라우트를 지운 뒤 타입 체크가 없는 파일을 찾는다

- **증상:** `/go/clinic` 라우트를 지우고 `make fe-check`를 돌리자 `tsc --noEmit`이 `.next/dev/types/validator.ts`에서 `src/app/go/clinic/page`를 찾을 수 없다며 실패했다. 소스에는 그 경로를 가리키는 코드가 없었다.
- **원인:** 개발 서버가 만든 라우트 타입 캐시(`frontend/.next/dev/types`)에 지운 라우트가 남아 있었다. `tsconfig.json`이 `.next/dev/types/**/*.ts`를 포함하고, `next typegen`은 `.next/types`만 다시 만들어서 개발 서버용 캐시는 그대로였다.
- **해결:** `frontend/.next/dev/types`를 지우고 다시 실행했다. 소스는 바꾸지 않았다.
- **배운 점:** 라우트를 지우거나 옮긴 뒤 타입 오류가 `.next/` 안의 파일에서 나면 소스가 아니라 캐시 문제다. CI는 캐시 없이 시작하므로 영향이 없다.

## 레즈메드 목록의 병원 데이터가 HTML이 아니라 JS 문자열 안에 있다

- **증상:** 병원 목록이 화면에는 보이는데, 병원별 위경도와 시·도는 HTML 요소에 없었다.
- **원인:** 지도 마커용으로 병원마다 `var html = "..."` 문자열과 `locations.push({...})`가 인라인 스크립트에 들어 있었다. 따옴표가 `\"`로 적힌 JS 문자열이라 DOM 파서로 읽을 수 없고, 페이지 끝에는 `${nameAttr}`이 들어간 템플릿 문자열도 섞여 있었다.
- **해결:** `var html = ` 기준으로 덩어리를 나누고 `locations.push`가 끝나는 `});`까지만 잘라 정규식으로 읽었다. 템플릿은 `var info = `로 시작해 덩어리에 들어오지 않는다. 구현 전에 저장해 둔 실제 페이지로 파서를 돌려 337건이 모두 읽히는지 확인했다.
- **남은 문제:** 원본 자체가 틀린 병원이 1곳 있다. 부산 `busancoent`의 병원명에 다른 병원 이름 5개가 붙어 있고(77자) 전화번호에 지역번호가 없다. 레즈메드 페이지의 HTML과 `name` 값이 모두 같은 상태라 파서 문제가 아니다. 올바른 이름을 추측해 넣지 않고 원본 그대로 둔다. 레즈메드가 고치면 다음 수집 때 반영된다.
- **배운 점:** 주소 뒤 우편번호는 앞자리 0이 빠진 값("6060", "0")이 섞여 있어 쓰지 않았다. 시·도 표기도 "강원도"·"서울"·"충북"처럼 섞여 있어 크롤러에서 약칭으로 통일하고, 모르는 값이 나오면 저장하지 않고 실패시키게 했다.

## 82cook 글 수집이 17건에서 연결 거부로 멈췄다

- **증상:** 가설 검증용으로 82cook 자유게시판 글 400건의 본문을 받으려 했는데, 17건째 이후 모든 요청이 `Connection refused`로 실패했다. 그 전까지는 검색 목록 96쪽과 본문 17건을 1.2초 간격으로 순서대로 받았다(합계 약 140회).
- **원인:** 사이트가 연결을 거부한 이유(IP 차단인지 일시 장애인지)는 확인하지 않았다. 확인된 것은 수집 스크립트의 결함이다. 차단 신호를 HTTP 403·429로만 판단했고, 연결 거부는 일반 실패로 처리했다. 실패했을 때 기다리는 시간도 없어서, 거부된 연결 시도 383건이 간격 없이 연달아 나갔다.
- **해결:** 수집을 멈췄고 다시 요청하지 않았다. 재개 여부와 방식은 정하지 않았다. 재개한다면 연결 오류를 차단으로 보고 첫 실패에서 즉시 멈추도록 고친 뒤, 간격을 크게 늘린다. IP나 User-Agent를 바꿔 우회하지 않는다.
- **배운 점:** 수집 스크립트의 "멈춤 조건"은 상태 코드만이 아니라 연결 오류까지 포함해야 하고, 실패는 연속 1회로도 멈춰야 한다. robots.txt가 허용해도 사이트가 받아주는 요청량은 따로 있다. 목록 수집(945건)과 본문 수집을 나누어 캐시해 둔 덕분에 목록은 다시 받지 않아도 된다.
