# 트러블슈팅 기록

> **목적:** 만들면서 막힌 문제를 증상, 원인, 해결, 배운 점으로 겪은 즉시 기록한다.
>
> **결론:** 7건이다. 크롤링(레즈메드 데이터가 JS 문자열 안에 있음, 좌표 6곳 중 1곳 오류, 출력 0바이트, 82cook 수집 차단), 개발(라우트 삭제 후 타입 체크), 광고 측정(메타 토큰 만료, GA4 실시간 확인). 공통으로 배운 점은 가져온 데이터와 외부 도구를 독립된 기준으로 한 번 더 확인하는 것이다.

## 라우트를 지운 뒤 타입 체크가 없는 파일을 찾는다

- **증상:** `/go/clinic` 라우트를 지우고 `make fe-check`를 돌리자 `tsc --noEmit`이 `.next/dev/types/validator.ts`에서 `src/app/go/clinic/page`를 찾을 수 없다며 실패했다. 소스에는 그 경로를 가리키는 코드가 없었다.
- **원인:** 개발 서버가 만든 라우트 타입 캐시(`frontend/.next/dev/types`)에 지운 라우트가 남아 있었다. `tsconfig.json`이 `.next/dev/types/**/*.ts`를 포함하고, `next typegen`은 `.next/types`만 다시 만들어서 개발 서버용 캐시는 그대로였다.
- **해결:** `frontend/.next/dev/types`를 지우고 다시 실행했다. 소스는 바꾸지 않았다.
- **배운 점:** 라우트를 지우거나 옮긴 뒤 타입 오류가 `.next/` 안의 파일에서 나면 소스가 아니라 캐시 문제다. CI는 캐시 없이 시작하므로 영향이 없다.

## 레즈메드 목록의 병원 데이터가 HTML이 아니라 JS 문자열 안에 있다

- **증상:** 병원 목록이 화면에는 보이는데, 병원별 위경도와 시·도는 HTML 요소에 없었다.
- **원인:** 지도 마커용으로 병원마다 `var html = "..."` 문자열과 `locations.push({...})`가 인라인 스크립트에 들어 있었다. 따옴표가 `\"`로 적힌 JS 문자열이라 DOM 파서로 읽을 수 없고, 페이지 끝에는 `${nameAttr}`이 들어간 템플릿 문자열도 섞여 있었다.
- **해결:** `var html = ` 기준으로 덩어리를 나누고 `locations.push`가 끝나는 `});`까지만 잘라 정규식으로 읽었다. 템플릿은 `var info = `로 시작해 덩어리에 들어오지 않는다. 구현 전에 저장해 둔 실제 페이지로 파서를 돌려 337건이 모두 읽히는지 확인했다.
- **남은 문제:** 원본 자체가 틀린 병원이 1곳 있다. 부산 `busancoent`의 병원명에 다른 병원 이름 5개가 붙어 있고(77자) 전화번호에 지역번호가 없다. 레즈메드 페이지의 HTML과 `name` 값이 모두 같은 상태라 파서 문제가 아니다. 올바른 이름을 추측해 넣지 않고 원본 그대로 둔다. 레즈메드가 고치면 다음 수집 때 반영된다.
- **배운 점:** 주소 뒤 우편번호는 앞자리 0이 빠진 값("6060", "0")이 섞여 있어 쓰지 않았다. 시·도 표기도 "강원도"·"서울"·"충북"처럼 섞여 있어 크롤러에서 약칭으로 통일하고, 모르는 값이 나오면 저장하지 않고 실패시키게 했다.

## 82cook 글 수집이 17건에서 연결 거부로 멈췄다

- **증상:** 가설 검증용으로 82cook 자유게시판 글 400건의 본문을 받으려 했는데, 17건째 이후 모든 요청이 `Connection refused`로 실패했다. 그 전까지는 검색 목록 96쪽과 본문 17건을 1.2초 간격으로 순서대로 받았다(합계 약 140회).
- **원인:** 사이트가 연결을 거부한 이유(IP 차단인지 일시 장애인지)는 확인하지 않았다. 확인된 것은 수집 스크립트의 결함이다. 차단 신호를 HTTP 403·429로만 판단했고, 연결 거부는 일반 실패로 처리했다. 실패했을 때 기다리는 시간도 없어서, 거부된 연결 시도 383건이 간격 없이 연달아 나갔다.
- **해결:** 수집을 멈췄고 다시 요청하지 않았다. 재개 여부와 방식은 정하지 않았다. 재개한다면 연결 오류를 차단으로 보고 첫 실패에서 즉시 멈추도록 고친 뒤, 간격을 크게 늘린다. IP나 User-Agent를 바꿔 우회하지 않는다.
- **배운 점:** 수집 스크립트의 "멈춤 조건"은 상태 코드만이 아니라 연결 오류까지 포함해야 하고, 실패는 연속 1회로도 멈춰야 한다. robots.txt가 허용해도 사이트가 받아주는 요청량은 따로 있다. 목록 수집(945건)과 본문 수집을 나누어 캐시해 둔 덕분에 목록은 다시 받지 않아도 된다.

## 크롤러 출력 파일이 0바이트가 됐다

- **증상:** 병원 좌표 교정 작업 중 `frontend/src/data/hospitals.json`이 빈 파일이 됐다.
- **원인:** 에이전트가 분석 명령에 `pnpm crawl | head -0`을 섞어 크롤이 한 번 더 돌았고, 파이프가 먼저 닫히면서 크롤러가 파일을 쓰다 말고 끝났다. 크롤러가 최종 파일에 바로 쓰고 있어서, 중간에 끊기면 빈 파일이 남는 구조였다.
- **해결:** `make crawl`을 다시 돌려 복구했다(레즈메드 요청은 합계 3회). 크롤러가 임시 파일에 다 쓴 뒤 이름을 바꾸도록 고치고, 저장 전에 필수 필드·좌표 범위·id 중복을 검사하게 했다.
- **배운 점:** 서비스가 읽는 파일은 "다 쓴 뒤 바꿔 끼우기"로 저장해야 중간에 끊겨도 이전 데이터가 남는다.

## 레즈메드 병원 좌표가 6곳 중 1곳꼴로 틀렸다

- **증상:** "내 주변 순으로 보기"에서 고양의 병원이 수원 근처로, 양주의 병원이 평택 근처로 정렬됐다. 공급 공백 분석 중 좌표와 주소의 시·군·구가 다른 병원 2곳이 눈에 띄었다.
- **원인:** 337곳을 심평원 "전국 병의원 및 약국 현황"의 좌표와 비교하니 52곳이 500m 넘게, 11곳이 5km 넘게(최대 43.5km) 어긋났다. 같은 페이지를 다른 정규식으로 다시 읽어도 같은 값이 나와 파서가 아니라 레즈메드 원본 오류였다. 주소가 경남인 병원 2곳은 레즈메드가 경북으로 분류했다.
- **해결:** 크롤러가 레즈메드 병원을 공공 데이터와 맞춰(전화+주소, 전화+이름, 주소+이름 순서. 전화번호만이나 이름만으로는 맞추지 않음) 좌표를 공공 데이터 값으로 바꾸고, 시·도는 주소 첫 단어로 다시 계산한다. 337곳 중 326곳을 맞췄다. 원 페이지 링크(`sourceUrl`)는 그대로 레즈메드다.
- **배운 점:** 크롤링한 데이터는 "가져왔다"에서 끝내지 않고 독립된 출처와 한 번 대조해야 한다. 한 건을 손으로 본 것으로는 52건이 보이지 않았다.

## 메타 광고 리포트가 토큰 만료로 실패했다

- **증상:** 광고 집행 첫날(10월 3일) `make meta-report`가 `메타 API 400: Error validating access token: Session has expired`(code 190, subcode 463)로 멈췄다. GA4 숫자도 같이 받지 못했다.
- **원인:** `.env.local`의 `META_ACCESS_TOKEN`이 그래프 API 탐색기에서 받은 단기 사용자 토큰이라 몇 시간 만에 만료됐다. 스펙은 만료 없는 시스템 사용자 토큰을 전제로 했다.
- **해결:** 비즈니스 설정에서 리포트 전용 시스템 사용자를 새로 만들고(자동 생성된 "Conversions API System User"는 쓰지 않음), 광고 계정 "광고 보기"와 앱을 할당한 뒤 `ads_read`만 준 만료 없는 토큰을 넣었다. 앱을 할당하지 않으면 토큰 생성 화면에 "사용 가능한 권한 없음"이 뜬다.
- **배운 점:** 외부 API 키는 "넣었다"가 아니라 "만료 조건까지 확인했다"로 끝내야 한다. 집행 전에 리포트를 한 번 돌려봤다면 미리 알았다.

## GA4 실시간 보고서에 체크 이벤트가 안 보였다

- **증상:** 광고로 랜딩 조회 5건이 잡혔는데 GA4 실시간 보고서가 비어 있었고, 테스트로 체크를 시작해도 `check_start`가 보이지 않았다.
- **원인:** 세 가지가 겹쳤다. ① 실시간 보고서는 최근 30분만 보여줘, 아침 방문자는 이미 빠져 있었다. ② Playwright 헤드리스 브라우저는 사용자 에이전트에 `HeadlessChrome`이 들어가 GA4가 봇으로 걸러냈다. ③ Playwright는 `sendBeacon` 요청을 실제로 보냈어도 `ERR_ABORTED`로 표시해, 전송 실패처럼 보였다. 앱 내장 브라우저 패널은 사이트 JS를 차단해 하이드레이션 자체가 안 됐다.
- **해결:** 코드 문제는 없었다. 일반 크롬 사용자 에이전트로 다시 보내자 `check_start`가 실시간에 잡혔다.
- **배운 점:** 분석 이벤트를 검증할 때는 테스트 도구가 분석 도구에 어떻게 보이는지(봇 필터, 집계 창, 전송 방식)부터 확인한다. 헤드리스 테스트에서 이벤트가 안 보이는 것만으로 수집이 깨졌다고 판단하지 않는다.
